# OpenChime: Architectural Decisions

A consolidated record of the architecture decisions made for OpenChime, a cross-platform business chat application with a self-hosted open-source core and a paid hosted tier.

Business, product, and scope decisions live in [REQUIREMENTS.md](./REQUIREMENTS.md).

## Server / Daemon

- **ARCH-1 (Language):** C daemon.
- **ARCH-2 (Persistence):** SQLite in WAL mode.
- **ARCH-3 (Replication):** Litestream for continuous replication to object storage (R2/B2), run as an unmodified external companion process (Apache 2.0), not embedded or reimplemented. Embedding it was evaluated (Go, `cgo -buildmode=c-shared`) and rejected — it would pull the Go runtime/GC into an otherwise pure-C daemon and complicate Windows/macOS cross-compilation. A from-scratch C reimplementation (via `sqlite3_wal_hook`, avoiding Litestream's external WAL-polling) was also evaluated and rejected for this project's current scope — Litestream's years of production hardening against WAL/checkpoint edge cases aren't worth re-earning for a durability-critical component.
- **ARCH-4 (Deployment):** Fly.io, single-box-per-tenant island model. Cost is driven by concurrent load and data volume, not registered user count. HA (second machine + LiteFS) and heavy media egress are the triggers that change the economics, not user count alone.
- **ARCH-5 (Threading):** Two-thread model. The network thread owns the socket and framing; the DB writer thread owns the single SQLite write connection.
- **ARCH-22 (Network concurrency model):** The network thread is a single-threaded event loop (epoll/kqueue) multiplexing all client connections with non-blocking I/O, not thread-per-connection and not a worker pool. Fits the lean per-tenant memory profile (ARCH-4) and matches the two-thread model literally.
- **ARCH-23 (Durability and RPO):** The daemon acks a client's message send after the local SQLite WAL commit only; it does not block on Litestream's remote shipment (ARCH-3). Litestream's sync interval is set to 15 seconds, so the system's stated RPO is up to 15s of committed-but-unshipped messages on total box loss. This was a deliberate cost/latency tradeoff: at a 1s interval, worst-case replication request cost was estimated at ~$11.66/tenant/month (Litestream batches all changes within an interval into one R2/B2 write request, so cost is bounded by interval length, not message volume); 15s cuts that roughly 15x, with realistic usage costing pennies.
- **ARCH-24 (Cold-start recovery):** On startup, if no local database file is present, the daemon always restores from the latest Litestream snapshot in R2/B2 before serving traffic. If a local file is present (a normal restart on the same disk), it is used as-is and Litestream simply resumes shipping.
- **ARCH-25 (Health check):** A dedicated lightweight HTTP endpoint (`/healthz`), separate from the binary-protocol port, for the deployment platform's orchestrator to poll — not a connection through the custom wire protocol.
- **ARCH-26 (Configuration source):** Per-tenant configuration (auth-mode block, DNS suffix, R2/B2 credentials) is a static config file read once at daemon startup. No runtime dependency on a reachable control plane, consistent with the single-box-per-tenant island model. The **auth-mode block** (ARCH-19/55) declares `local` or `oidc`; for `oidc` it carries central's pinned public key + this instance's audience id (ARCH-56/57); for `local` it carries the one-time owner-bootstrap setup token (ARCH-59). Note the daemon config no longer holds provider OIDC/JWKS endpoints — those live in the central service (ARCH-56), not the daemon.
- **ARCH-27 (Schema migrations):** Sequential migrations are embedded in the daemon binary, numbered, and applied automatically against a `schema_version` table on startup, inside a transaction, before the daemon serves traffic. No separate migration tool or manual operator step. Concrete design and the schema itself are in [SCHEMA.md](./SCHEMA.md).
- **ARCH-49 (Migration runner design):** The embedded migrations are an ordered C array (`{version, sql}`, versions strictly increasing from 1). The runner applies each pending migration **in its own transaction**, recording the version in the `schema_version` table on commit — so a failure rolls back only that step and leaves the database at the last good version, and a restart resumes from exactly there (rather than wrapping all pending steps in one transaction). Migrations are forward-only: there are no down-migrations; recovery from a bad migration is roll-forward or restore from the Litestream replica (ARCH-24), consistent with the single-box model. Implemented in `src/migrate.c`, unit-tested per TESTING.md §2.2.
- **ARCH-51 (TLS library):** TLS is mbedTLS (Apache-2.0), pinned at 3.6 LTS and vendored/built from source (`scripts/build_mbedtls.sh` into `third_party/`, gitignored) so local, CI, and the Docker image share one version — chosen over OpenSSL and LibreSSL for its lean pure-C footprint (ARCH-4/REQ-210), easy cross-compilation to the three client platforms (ARCH-11), in-process self-signed cert generation via `x509write` (ARCH-10), and a verify callback for TOFU pinning. Distro packages were rejected because Ubuntu ships 2.28 and Alpine ships 3.6.x with source-incompatible APIs. `src/tls.c` wraps it for the non-blocking epoll loop (ARCH-22) and enforces TOFU: the client uses `VERIFY_OPTIONAL` + a fingerprint-checking callback (no CA chain exists, so `VERIFY_REQUIRED` can't be used), and rejects a pin mismatch after the handshake. Details in [TLS.md](./TLS.md).
- **ARCH-50 (Core schema, migration 0001):** The first migration establishes the foundational tables for the core messaging path — `users`, `channels`, `channel_members`, `messages`, `sent_messages` — detailed in [SCHEMA.md](./SCHEMA.md) §2. It gives physical form to already-decided requirements: `messages.id` is `AUTOINCREMENT` for the tenant-monotonic message id (ARCH-43); deletion is a tombstone with a `deleted_by` column, not a row removal (REQ-052, REQ-032); edits keep the original timestamp and set `edited_at_ms` (REQ-051); and `sent_messages` is the idempotency map (ARCH-44). Its one genuinely new storage decision is `channel_members` as the membership set, resolving REQ-031. Roles (REQ-030/033), reactions, threads, FTS5 (ARCH-15), presence, notifications, and attachments are deliberately deferred to later migrations, listed in SCHEMA.md §3.
- **ARCH-52 (Event loop and message vertical):** The two-thread model (ARCH-5) and single-threaded epoll network loop (ARCH-22) are realized across `src/netloop.c` (accept + per-connection TLS + frame dispatch), `src/framebuf.c` (incremental frame reassembly implementing the ARCH-9 two-phase read over a bounded buffer), `src/dbwriter.c` (the DB-writer thread that owns the write connection and runs migrations on boot), and `src/tls.c` (ARCH-10/51). Connections use non-blocking I/O with epoll interest re-armed from mbedTLS `WANT_READ`/`WANT_WRITE`. The **net thread ↔ DB-writer thread hand-off** is a job/result queue: the net thread submits AUTH/SEND jobs and is woken to collect results by the writer's **eventfd** registered in epoll, so all socket I/O stays on the net thread and all DB writes on the writer. The loop implements handshake → `WELCOME`/`REJECT` (PROTOCOL.md §3), AUTH → `AUTH_OK`, `SEND` → persist (monotonic id ARCH-43, idempotency ARCH-44) → `SEND_ACK` to the sender + `BROADCAST` to the channel's connected members (REQ-090/092), and reconnect backfill (REQ-100/101): a `BACKFILL_REQUEST` becomes a read job that replays `id > cursor` messages (membership-checked, bounded) as `BROADCAST`s followed by `BACKFILL_DONE` (ARCH-46). **AUTH is currently stubbed** (the token is upserted as a user subject, with a default channel auto-joined) — the real two-mode auth + session design (ARCH-19/55–60, [AUTH.md](./AUTH.md)) replaces it as a follow-on milestone. `src/main.c` wires these together with the `/healthz` responder (ARCH-25).
- **ARCH-53 (Logging):** The daemon logs to **stderr**, not syslog. Under systemd (self-hosted `.deb`, ARCH-20) journald captures stderr automatically (`journalctl -u openchimed`); in the Fly.io/Docker container (ARCH-4/36) the runtime collects stdout/stderr — whereas a container typically has no syslog daemon, so `syslog()` would go nowhere. This is the standard "log to stderr, let the supervisor route it" model; a self-hoster wanting syslog can set journald's `ForwardToSyslog`. A leveled-logging helper (info/warn/error with timestamps) is a later refinement of the destination, not a change to it.
- **ARCH-28 (Packaging and process model):** One binary, multiple processes. The daemon self-forks (or re-execs itself with a mode flag, e.g. `openchimed --mode=audio-sidecar`) to run companion processes like the audio relay (ARCH-18) as separate OS processes. Process isolation comes from `fork()`, not from being a separate build artifact, so this gets the same crash-isolation property as a separate binary while keeping one build artifact and a guaranteed version match between the daemon and its sidecars.
- **ARCH-29 (Upgrade rollout):** Restart-and-reconnect. A new daemon binary replaces the old one and restarts the process; connected clients see a dropped connection and reconnect automatically via the mechanism REQ-100/REQ-101 already require. No graceful connection draining — not worth the added complexity for a single-box, hobby-scale system.

## Wire Protocol

- **ARCH-6 (Decision):** Custom length-prefixed, versioned binary protocol over TLS/TCP. Not HTTP, not WebSocket, not JSON. Justified because both ends (C daemon and C client) are built together, removing any reason to pay HTTP/JSON overhead.
- **ARCH-7 (Serialization):** Explicit field-by-field; no struct memcpy.
- **ARCH-8 (Frame layout):** Fixed header of `length` (u32, network byte order), `version` (u8/u16), `msg_type` (u16), followed by a type-specific payload.
  - `length`: total bytes after this field; makes the stream self-framing over TCP's boundary-less byte stream.
  - `version`: checked on the first frame so incompatible clients are rejected cleanly rather than misparsed.
  - `msg_type`: enum discriminating login, message-send, message-broadcast, presence-update, ack, error, etc.
- **ARCH-9 (Reading discipline):** Network thread reads in two phases (fixed header, then `length` more bytes), each looping to handle partial TCP reads. Everything is network byte order, converted at the edges.
- **ARCH-10 (TLS):** The daemon generates its own self-signed certificate on first run. Clients trust it via TOFU (trust-on-first-connect) pinning, with the fingerprint optionally published in the `.well-known` discovery metadata (ARCH-14) for out-of-band verification. This applies uniformly to hosted and self-hosted tiers — no ACME, no Let's Encrypt, no certificate renewal machinery anywhere in the baseline system. Standard PKI was the original design but was dropped: the client is a native binary under the maintainer's control, not a browser, so it doesn't need CA-chain trust; and mandatory ACME is impossible for a self-hosted, internet-unreachable deployment (e.g. an air-gapped MSP client network), since ACME requires public HTTP reachability or a public DNS API. This is a different axis from the earlier per-operator cert-pinning design that was dropped in favor of a generic client — that was build-time pinning tied to per-operator binaries; TOFU is dynamic, runtime pinning, fully compatible with one generic client. The one exception is the incoming-webhooks endpoint (see "HTTP and Webhooks" below), which does need a CA-signed cert.
- **ARCH-30 (Protocol limits):** Conservative small-team defaults: max frame size and max message body size are ~64KB, and max concurrent connections per tenant is in the low hundreds. Attachments are never sent as protocol frames — they go through the object-storage path (ARCH-17) exclusively. The byte-exact limits (`MAX_FRAME_SIZE` = 65 KiB, `MAX_BODY_SIZE` = 64 KiB) are fixed in [PROTOCOL.md](./PROTOCOL.md) §2.1.
- **ARCH-41 (Handshake and version negotiation):** A connection opens with a client `HELLO` advertising the inclusive `[min_version, max_version]` range it supports; the server replies `WELCOME` with a single chosen version used by both sides thereafter, or `REJECT` with a reason code. The `HELLO`/`WELCOME`/`REJECT` frames are frozen at version 1 forever so negotiation itself can never hit a version mismatch. `REJECT` distinguishes `VERSION_TOO_OLD` (client outdated — prompt "update the app") from `VERSION_TOO_NEW` (daemon behind — operator must upgrade, do not prompt the user), resolving REQ-111. First-frame-must-be-`HELLO` and pre-parse version validation resolve REQ-110. Detailed layout in [PROTOCOL.md](./PROTOCOL.md) §3.
- **ARCH-42 (Primitive field encodings):** All frames are composed from a fixed primitive set — `u8/u16/u32/u64` big-endian, `str` (u16-length UTF-8), `lstr` (u32-length UTF-8 for message bodies), `bytes` (u32-length raw), and `idem` (fixed 16-byte token) — encoded explicitly field-by-field with no struct `memcpy`, realizing ARCH-7. Timestamps are `u64` ms since Unix epoch UTC; ids are `u64`. Catalogued in [PROTOCOL.md](./PROTOCOL.md) §7.
- **ARCH-43 (Message id allocation):** Message ids are server-assigned `u64`, monotonic per tenant, allocated by the single DB-writer thread (ARCH-5) inside the WAL commit. Tenant-monotonicity means ascending id order equals accept order within a channel, which is what makes REQ-092's per-channel ordering guarantee and the client dedup high-water mark (ARCH-45) fall out for free.
- **ARCH-44 (Idempotency mapping):** A `SEND` carries a client-generated 16-byte idempotency token; the daemon persists a `(channel_id, idempotency_token) → message_id` mapping in SQLite and, on a repeat token, re-returns the original `SEND_ACK` instead of storing a second copy. This makes an unacked send safely retryable (REQ-093) and de-duplicates offline-composed messages re-sent on reconnect (REQ-102). The mapping is pruned after a bounded retention window (target 24h), long enough to cover realistic reconnect-retry.
- **ARCH-45 (Client-side dedup):** A client keeps a per-channel high-water mark of the highest `message_id` seen and suppresses any `BROADCAST` with `message_id <=` that mark as a redelivery, satisfying REQ-091's at-least-once duplicate suppression. The dedup key is the server message id (ARCH-43); the window is the client's persisted per-channel mark.
- **ARCH-46 (Reconnect backfill shape):** On reconnect the client sends `BACKFILL_REQUEST` carrying a per-channel `{channel_id, after_message_id}` cursor list; the server replays `BROADCAST` frames for `message_id >` each cursor in ascending order per channel, terminated by `BACKFILL_DONE`. Per-channel (not a single global) cursors are required because cross-channel ordering carries no guarantee (REQ-092), so a single global cursor could skip a low id still missing in one channel while a higher id was already acked in another. Resolves REQ-101. Detailed in [PROTOCOL.md](./PROTOCOL.md) §6.
- **ARCH-47 (Error frame and code table):** Post-handshake errors use a single `ERROR` frame carrying a `u16` reason code, a `fatal` flag (whether the connection closes), an optional `context` blob (the offending idempotency token on a failed `SEND`), and a human-readable message; handshake-stage version errors use `REJECT` with the same code space. Codes are grouped by range (1000 protocol/version, 2000 auth, 3000 messaging, 9000 internal) so a client can categorize an unrecognized code. Full table in [PROTOCOL.md](./PROTOCOL.md) §8.

## Client

- **ARCH-11 (Language):** Native C, explicitly rejecting Electron.
- **ARCH-12 (Rendering path):** raylib for window/paint/input, with HarfBuzz for text shaping and a Unicode line-break library for the message view. Lexbor evaluated but ruled out as a text-rendering engine (its layout/paint pipeline is not production-ready; only the HTML/CSS parser and DOM are stable).
- **ARCH-13 (Generic client):** A single generic client replaced the earlier per-operator custom-binary approach.

## Discovery

- **ARCH-14 (Rule):** Instance-address, resolved by plain DNS — there is no hosted resolution service. At sign-in the client collects the **instance** (the tenant's address) plus the user's **email** directly, the same model as Slack's "enter your workspace URL." The instance is turned into a daemon address by ordinary DNS, with no shared, always-on, cross-tenant lookup component to run: consistent with the single-box-per-tenant island model (ARCH-4) and the "no runtime dependency on a reachable control plane" stance (ARCH-26). Two forms:
  - **Self-hosted:** the user supplies a full domain (e.g. `chat.acme.com`), resolved via SRV records plus optional `.well-known` metadata (which may also carry the TOFU cert fingerprint per ARCH-10). Nothing hosted is involved.
  - **Hosted tier:** the user supplies a bare name (e.g. `acme`); the client appends the service's known DNS suffix as a pure client-side string convention (`acme` → `acme.openchime.example`) and resolves the result by plain DNS. The per-tenant DNS record is provisioned when the tenant is created — DNS *is* the name→address map, so no custom registry service exists. The user may equivalently type the full `acme.openchime.example`.
  - **Self-hoster vanity name (optional, free):** a self-hoster may request a DNS record under the service suffix (e.g. a CNAME `acme.openchime.example` → their own box) so their users get the same short-name experience as hosted tenants without the self-hoster owning or configuring public DNS. This stays a pure DNS record, not a runtime service, so it does not reintroduce the resolution layer or the island model's shared-component problem. It composes cleanly with TOFU TLS (ARCH-10): because the client pins whatever self-signed cert the daemon presents rather than validating a CA chain against the hostname, a name under someone else's domain "just works" with no cert coordination — a synergy that a CA-cert design would not have. The box remains fully self-hosted (operator's config, R2, and data per ARCH-4/ARCH-26); only the discovery name lives under the service suffix.
  - **Port:** resolution yields a port as well as a host, with precedence SRV-record port > `.well-known` `port` field > the default 443 (ARCH-54). A self-hoster on a non-standard port is honored automatically via SRV; hosted tenants use 443.
  - The email is used only to drive the OIDC login (ARCH-19); it is not used to derive the instance (a hosted tenant's email domain does not reveal its hosted address without a registry, which this design deliberately avoids). This supersedes the earlier "dot-based, resolve bare names via a hosted resolution service" rule, which required the shared cross-tenant component that ARCH-4's island model otherwise avoids; see REQ-041.

## Feature Implementation

- **ARCH-15 (Search):** FTS5 full-text search, positioned as a competitive wedge against Slack's history caps.
- **ARCH-16 (Notifications delivery):** Push via APNs/FCM (free from providers). Self-hosted deployments need a small push gateway since the app is published under the maintainer's accounts.
- **ARCH-17 (Attachments):** Via object storage.
- **ARCH-18 (Audio conferencing):** Server-relay (no P2P/ICE), Opus codec, delivered as an isolated UDP-based sidecar process rather than embedded in the daemon's TCP loop.
- **ARCH-31 (Audio sidecar IPC):** The daemon and the audio sidecar process (ARCH-18, ARCH-28) communicate over a Unix domain socket — native POSIX IPC via the same `socket()` API already used for TCP, no extra library, no network exposure.

## HTTP and Webhooks

- **ARCH-32 (Embedded HTTP listener):** The daemon embeds an HTTP/1.1 listener, fed from the same event loop as the binary-protocol listener (ARCH-22). It shares TLS port 443 with the binary protocol, demultiplexed by ALPN rather than sitting on a separate port (see ARCH-54 — this supersedes the earlier "separate port on 80/443" phrasing). Parsing uses picohttpparser (MIT/Perl dual-licensed, a single `.c`/`.h` request/header parser with no bundled socket or TLS handling and no competing event loop) — not a general embedded web server. Mongoose was ruled out (GPLv2/commercial dual license, not MIT/BSD); civetweb was ruled out because it brings its own connection-handling loop that would compete with ARCH-22's event loop. This endpoint serves the incoming-webhook receiver (REQUIREMENTS.md REQ-170) and the health check (ARCH-25).
- **ARCH-33 (No HTTP/2):** The webhook/health HTTP surface is plain HTTP/1.1 only, matching ARCH-6's existing rejection of HTTP overhead for the core protocol. Webhook senders are third parties making single, independent requests; HTTP/2's multiplexing has no benefit for that pattern.
- **ARCH-34 (Webhook TLS):** A CA-signed certificate is obtained on-demand, feature-gated to tenants that enable webhooks — not a baseline daemon requirement (ARCH-10). This is the one surface where TOFU pinning doesn't work: third-party webhook senders (GitHub, Zapier, scripts) are not under the operator's control and validate TLS against a standard CA trust store with no ability to pin a custom cert. Because the HTTP surface shares port 443 with the binary protocol via ALPN (ARCH-54), the daemon presents this CA cert to connections that do not negotiate the `oc/1` ALPN (typically selected by SNI matching the webhook hostname) and the self-signed cert (ARCH-10) to `oc/1` connections.
- **ARCH-54 (Ports and ALPN multiplexing):** The public port is **443** for all external traffic — the binary protocol and the HTTP/webhook surface (ARCH-32) share it, demultiplexed by **ALPN** negotiated in the TLS handshake: a client offers `oc/1` (`OC_ALPN_PROTO`) and is routed to the binary-protocol handler; anything else (e.g. an HTTPS webhook sender) is routed to the HTTP/1.1 handler. 443 was chosen because it is the one port restrictive networks reliably allow outbound and the only port third-party webhook senders speak; a high port would work for the app clients in most environments (outbound high ports are usually open) but not for the webhook case, and standardizing avoids a per-environment variable. The daemon binds a configurable `OPENCHIME_PROTO_PORT` (production 443 — self-hosted via a systemd `CAP_NET_BIND_SERVICE` grant per ARCH-20, hosted via Fly's external→container port map; dev binds unprivileged 8443). **Clients** dial the port from discovery with precedence SRV-record port > `.well-known` `port` > `OC_DEFAULT_PORT` (443). The `oc/1` ALPN and the 443 default are a fixed client-facing contract established now (in `src/tls.c`, both server and client) so clients conform from first release even though the HTTP handler is a later milestone; the `/1` suffix versions the transport-framing generation, separate from the per-frame `version` (ARCH-8). Full detail in [PROTOCOL.md](./PROTOCOL.md) §1.1.

## Authentication

Full design and rationale in [AUTH.md](./AUTH.md).

- **ARCH-19 (Architecture):** Two authentication modes selected per deployment (ARCH-55), converging on a daemon-issued session (ARCH-58). In **local mode** the daemon is the identity authority (username+password, ARCH-59). In **OIDC mode** the login is a client-drives-browser flow with PKCE using platform-native auth session APIs (ASWebAuthenticationSession on iOS/macOS, loopback redirect on desktop), but the OIDC Relying Party is the maintainer's **central service** (ARCH-56), not the daemon: the daemon validates a compact token that the central service re-issues (ARCH-57), never a raw provider JWT and never provider JWKS. This supersedes the original "the daemon validates the returned JWT against provider JWKS" rule — that pulled JSON/JWKS/provider handling into the lean C daemon and gave self-hosters no path to social login without registering their own provider apps.
- **ARCH-55 (Two-mode auth framework):** Authentication is **local** (daemon-managed accounts, for standalone/air-gapped self-hosters) or **OIDC-via-central** (social login brokered by the maintainer's central service, for the hosted tier and self-hosters who opt in via a relay). There is deliberately no "daemon speaks OIDC directly to your own IdP" mode — OIDC always routes through central — which keeps the daemon free of OIDC/JWKS/JSON and means self-hosters never hold provider credentials. A deployment picks one mode in config (ARCH-26); the daemon advertises it in-protocol via `AUTH_CHALLENGE` (PROTOCOL.md §4). Both modes converge on a daemon-issued session (ARCH-58), so all messaging/reconnect/revocation is mode-agnostic. v1 is one mode per tenant; both-at-once is deferred.
- **ARCH-56 (Central OIDC service + relay):** The maintainer runs a central service that holds the real Google/Microsoft/Apple app credentials, runs the Authorization-Code-+-PKCE flow, and re-issues a compact OpenChime identity token (ARCH-57) audience-scoped to the target instance. The **client is the courier** — it carries the token from central to the daemon, so central never connects to a self-hosted daemon (preserving the island model, ARCH-4). Trust is a public key the daemon pins from config (bundled in the distribution); the dependency on central is **login-time only** (issued sessions survive a central outage; local mode has no central dependency). This is a shared, login-time, identity-only component in OIDC mode — reconciled with REQ-041 (the message/data path stays island-isolated). The central service is a separately-built web component; the daemon side is tested with a test issuer.
- **ARCH-57 (Compact identity token):** Central signs a compact, field-encoded token (`version | subject | email | display_name | audience | issued_at_ms | expires_at_ms | ECDSA-P256 signature`), using the same primitive encodings as the wire protocol (ARCH-7), not a JSON JWT. The daemon verifies the ECDSA-P256 signature with mbedTLS (already linked; Ed25519 is not supported in mbedTLS, hence P-256), and checks `audience == this instance` (no cross-instance replay) and expiry. A JWT was rejected because it forces a JSON parser into the lean daemon for no benefit when both ends are ours — the same reasoning as ARCH-6.
- **ARCH-58 (Daemon-issued session tokens):** After any successful auth, the daemon mints a random 32-byte session token returned to the client and stores only its SHA-256 (leak-resistant) with user id + expiry + last-seen in a `sessions` table (SCHEMA.md migration 0002). Reconnect re-presents the token (no re-auth, REQ-100); the session lifetime is the daemon's, not a provider token's (REQ-181); revocation is a row delete (REQ-182 — the local session table the flag asked for). This convergence makes everything downstream mode-agnostic.
- **ARCH-59 (Local-auth credential model):** Local accounts use username+password hashed with PBKDF2-HMAC-SHA256 (mbedTLS `mbedtls_pkcs5_pbkdf2_hmac`, per-user salt, ~600k iterations) — chosen to add no new dependency (mbedTLS has no argon2; argon2 is a future vendored upgrade). The first owner is bootstrapped from a one-time setup token (config/log, no email → air-gapped-safe); further users are created by invite token. Failed attempts are rate-limited per account and per source (resolves REQ-191). Passwords travel only inside TLS (REQ-180) and only the hash is stored.
- **ARCH-60 (Role storage and enforcement):** Every user holds one tenant role — `owner`/`admin`/`member` — stored as a `role` column on `users` (migration 0002). Enforcement lives in the DB-writer handlers (the single write path): the ≥1-owner invariant (REQ-030), admin/owner moderation delete via `messages.deleted_by` (REQ-032), and owner/admin-only tenant invite/remove (REQ-033). Resolves the role storage/enforcement `[needs ARCH decision]`.

## Packaging and Distribution

- **ARCH-20 (Linux, self-hosted):** apt / `.deb` with a systemd unit, from a GPG-signed repo hosted on R2.
- **ARCH-21 (Windows):** Microsoft Store via MSIX packaging, chosen to avoid an Authenticode cert purchase.

## Local Development and Build

- **ARCH-35 (Build system):** A single hand-written `Makefile` (no CMake, no autotools), mirroring the sibling OpenBounty project's convention.
- **ARCH-36 (Local dev/test harness):** Docker Compose, not QEMU or Firecracker. Fly.io actually runs machines on Firecracker microVMs — Docker only shares the host kernel via namespaces/cgroups, so this doesn't replicate that isolation boundary — but it's the format Fly.io itself ingests as a build artifact (a Dockerfile becomes a Firecracker rootfs via `flyctl deploy`), and was chosen for local iteration speed and simplicity over fidelity.
- **ARCH-37 (Local base image):** Alpine (musl libc), matching the lean 256MB-per-tenant memory target (ARCH-4/REQUIREMENTS.md REQ-210). Litestream's glibc-linked release binary runs on it via the `gcompat` compatibility shim rather than a from-source build.
- **ARCH-38 (Local S3 simulation):** MinIO stands in for R2/B2 in the local Docker Compose environment, over LocalStack (heavier, broader-than-needed AWS emulation) and SeaweedFS (less battle-tested against Litestream specifically). MinIO server is AGPLv3-licensed; this is a dev/test-only dependency run via Compose, never embedded or distributed with OpenChime's own code, so no obligation attaches.
- **ARCH-39 (Local Litestream placement and sequencing):** Litestream runs in the same container as the daemon, matching the real single-box-per-tenant topology (ARCH-3/ARCH-4) where it needs direct filesystem access to the daemon's local SQLite file. The container's entrypoint sequences startup explicitly: attempt restore from the replica (ARCH-24) if no local DB file exists, fall back to initializing a fresh database if no replica exists either, start `litestream replicate` in the background, then exec the daemon in the foreground — avoiding a race where Litestream starts watching a file that doesn't exist yet.
- **ARCH-40 (Dev convenience scripts):** A `Scripts/` directory wraps the Docker Compose workflow: `run.sh` (build + start + block until the health check passes), `stop.sh` (stop, preserving local volumes), `reset.sh` (stop and wipe local volumes, for exercising the restore-on-boot path from a clean slate). These are thin wrappers with no behavior of their own beyond what `docker compose` already does directly — they exist to remove manual steps (creating `.env`, polling `/healthz`, remembering the container-removal-before-volume-removal ordering), not to hide anything.
- **ARCH-48 (Test strategy and CI):** Two tiers, detailed in [TESTING.md](./TESTING.md). Unit tests are hand-rolled (a ~15-line `CHECK` macro, no vendored framework), live in `tests/`, `#include` the `.c` under test directly to reach file-static helpers, and run via `make test` compiled `-O0 -g` — the same convention as the sibling C project openblocks. They cover pure logic: the frame codec (the first target), migration runner, idempotency/dedup, rate limiter, and the protocol state machine, using an injectable clock/id source for determinism. Integration tests drive the daemon with an in-repo C test client that **links the same `src/protocol.c` the daemon uses** — not a second-language reimplementation that could silently drift from the wire format — run against the existing Docker Compose stack (ARCH-36/38/39) so replication (ARCH-23) and restore-on-boot (ARCH-24) are proven against real Litestream + object storage. CI is GitHub Actions triggered on PRs to `main` (doc-only changes skipped), mirroring openblocks' `paths-ignore`/`concurrency` conventions: a `build` job (compile + `make test`) and an `integration` job automating the README's replication + restore verification. The client-side TLS library needed for socket-level integration scenarios is not yet decided and is flagged in TESTING.md §3.1 as part of the daemon TLS work.
