# OpenChime: Architectural Decisions

A consolidated record of the architecture decisions made for OpenChime, a cross-platform business chat application available in three deployment models (ARCH-76): self-hosted stand-alone, self-hosted federated, and hosted.

Business, product, and scope decisions live in [REQUIREMENTS.md](./REQUIREMENTS.md).

## Deployment Models

- **ARCH-76 (Deployment models):** OpenChime is deployed in exactly **three** models. Every other decision in this document is written against them, and any decision whose behavior differs by model says so explicitly.

  1. **Self-hosted stand-alone.** The operator runs the daemon, owns the data, and depends on **no** OpenChime-operated service at runtime. Local auth (ARCH-55), their own domain and DNS (ARCH-14), their own object storage (ARCH-3/70). The tradeoff is that federated-only features are simply absent — most visibly **mobile push, which is unavailable in this model** (ARCH-16): the published mobile clients are signed under the project's developer accounts, so push cannot be delivered without the project's gateway.
  2. **Self-hosted federated.** The operator still runs the daemon and owns **all message data**, but opts in to OpenChime-operated services for functions that are impractical to self-run. The federated set is: **OIDC login** (ARCH-56), **push delivery** (ARCH-16), the **app/integration directory** (REQ-175), **SCIM provisioning** (REQ-253), an optional **DNS name under the service suffix plus the workspace/audience registry** (ARCH-14), and **package distribution** (ARCH-20). Each is opt-in and independently declinable; declining all of them is exactly model 1.
  3. **Hosted.** OpenChime operates the daemon and the federated services on the customer's behalf. Architecturally this is model 2 plus operating the box — the daemon is the same binary with the same per-tenant isolation (ARCH-4).

  **The invariant across all three:** a federated service brokers *identity, notification, discovery, and provisioning metadata only* — **no OpenChime-operated service is ever in the message/data path**, and none can read message content, in any model (REQ-040/041). This is what makes federation safe to opt into: a federated self-hoster gives up no data sovereignty relative to a stand-alone one, only independence of availability.

  Note the difference between *federated* and *static*: a DNS record or a signed package repo is maintainer-provided but is not a request-serving component in any tenant's path. They are listed as federated above because they are dependencies on the project, not because they process traffic.

## Server / Daemon

- **ARCH-1 (Language):** C daemon.
- **ARCH-2 (Persistence):** SQLite in WAL mode.
- **ARCH-3 (Backup and replication — out of scope for this repo):** The daemon commits to its local SQLite database and has **no replication or backup component**. Continuous replication is a **hosted-model concern** (ARCH-76) and lives in the `openchime-saas` repo, which operates the boxes it deploys; nothing about it is configured, packaged, or documented here. A self-hosted operator (stand-alone or federated) backs up the SQLite file by whatever means they already use for the box — the database is a single file in WAL mode, so any snapshot or file-level backup tool applies.
- **ARCH-4 (Deployment topology):** **One box, one daemon, one SQLite database per tenant** — the "island model" — in all three deployment models (ARCH-76). A self-hoster runs that box themselves; in the hosted model the project runs it on Fly.io. Cost (hosted) is driven by concurrent load and data volume, not registered user count. HA (second machine + LiteFS) and heavy media egress are the triggers that change the economics, not user count alone. The island model is a statement about *tenant data isolation* — no tenant's data shares a process or a database with another's — and it holds regardless of which federated services (ARCH-76) a deployment opts into, because none of them are in the message/data path.
- **ARCH-5 (Threading):** Two-thread model. The network thread owns the socket and framing; the DB writer thread owns the single SQLite write connection. (Refined by ARCH-66: a third thread with a read-only connection serves query jobs so a heavy read can't stall the writer.)
- **ARCH-22 (Network concurrency model):** The network thread is a single-threaded event loop (epoll/kqueue) multiplexing all client connections with non-blocking I/O, not thread-per-connection and not a worker pool. Fits the lean per-tenant memory profile (ARCH-4) and matches the two-thread model literally.
- **ARCH-23 (Durability):** The daemon acks a client's message send **after the local SQLite WAL commit only** — it never blocks the ack on any off-box operation. A message is durable on the tenant's own disk before its sender is told it was accepted. What happens beyond the local commit (off-box backup, and therefore the deployment's recovery-point objective) is not this repo's concern: see ARCH-3 and REQ-094.
- **ARCH-24 (Cold-start recovery) — withdrawn, see ARCH-3.** Restore-from-replica was part of the replication design that moved to the hosted repo. In this repo a daemon that starts with no database file simply creates and migrates a fresh one; recovering an existing database onto a new box is the operator's (or, in the hosted model, the SaaS's) responsibility.
- **ARCH-25 (Health check):** A dedicated lightweight HTTP endpoint (`/healthz`), separate from the binary-protocol port, for the deployment platform's orchestrator to poll — not a connection through the custom wire protocol. The same listener also serves a **static landing page** on every other path (`daemon/main.c`): a workspace address is a natural thing to paste into a browser, so a human who does gets a small "an OpenChime workspace is running here, open it in a client" page rather than a 404 or a raw reset. It is deliberately identity-free — no workspace name, user list, or version — so an unauthenticated stranger learns only that the daemon is up.
- **ARCH-26 (Configuration source):** Per-tenant configuration (auth-mode block, DNS suffix, R2/B2 credentials) is a static config file read once at daemon startup. **The daemon never fetches its configuration from a control plane at runtime, in any deployment model (ARCH-76)** — a federated deployment's opted-in services (ARCH-56 OIDC, ARCH-16 push) are contacted for their own function, never to tell the daemon how to run. So a stand-alone deployment has no runtime dependency on the project at all, and a federated one keeps serving messages normally when the federated services are unreachable (it loses OIDC login and push, not the message path). The **auth-mode block** (ARCH-19/55) declares `local` or `oidc`; for `oidc` it carries central's pinned public key + this workspace's audience id (ARCH-56/57); for `local` it carries the one-time owner-bootstrap setup token (ARCH-59). Note the daemon config no longer holds provider OIDC/JWKS endpoints — those live in the central service (ARCH-56), not the daemon.
- **ARCH-27 (Schema migrations):** Sequential migrations are embedded in the daemon binary, numbered, and applied automatically against a `schema_version` table on startup, inside a transaction, before the daemon serves traffic. No separate migration tool or manual operator step. Concrete design and the schema itself are in [SCHEMA.md](./SCHEMA.md).
- **ARCH-49 (Migration runner design):** The embedded migrations are an ordered C array (`{version, sql}`, versions strictly increasing from 1). The runner applies each pending migration **in its own transaction**, recording the version in the `schema_version` table on commit — so a failure rolls back only that step and leaves the database at the last good version, and a restart resumes from exactly there (rather than wrapping all pending steps in one transaction). Migrations are forward-only: there are no down-migrations; recovery from a bad migration is roll-forward (a new migration) or restore from the operator's own backup (ARCH-3), consistent with the island model (ARCH-4). Implemented in `daemon/migrate.c`, unit-tested per TESTING.md §2.2.
- **ARCH-51 (TLS library):** TLS is mbedTLS (Apache-2.0), pinned at 3.6 LTS and vendored/built from source (`scripts/build_mbedtls.sh` into `third_party/`, gitignored) so local, CI, and the Docker image share one version — chosen over OpenSSL and LibreSSL for its lean pure-C footprint (ARCH-4/REQ-210), easy portability across the platforms the client core targets (ARCH-11/74), in-process self-signed cert generation via `x509write` (ARCH-10), and a verify callback for TOFU pinning. Distro packages were rejected because Ubuntu ships 2.28 and Alpine ships 3.6.x with source-incompatible APIs. `shared/tls.c` wraps it for the non-blocking epoll loop (ARCH-22) and enforces TOFU: the client uses `VERIFY_OPTIONAL` + a fingerprint-checking callback (no CA chain exists, so `VERIFY_REQUIRED` can't be used), and rejects a pin mismatch after the handshake. Details in [TLS.md](./TLS.md).
- **ARCH-50 (Core schema, migration 0001):** The first migration establishes the foundational tables for the core messaging path — `users`, `channels`, `channel_members`, `messages`, `sent_messages` — detailed in [SCHEMA.md](./SCHEMA.md) §2. It gives physical form to already-decided requirements: `messages.id` is `AUTOINCREMENT` for the tenant-monotonic message id (ARCH-43); deletion is a tombstone with a `deleted_by` column, not a row removal (REQ-052, REQ-032); edits keep the original timestamp and set `edited_at_ms` (REQ-051); and `sent_messages` is the idempotency map (ARCH-44). Its one genuinely new storage decision is `channel_members` as the membership set, resolving REQ-031. Roles (REQ-030/033), reactions, threads, FTS5 (ARCH-15), presence, notifications, and attachments are deliberately deferred to later migrations, listed in SCHEMA.md §3.
- **ARCH-52 (Event loop and message vertical):** The two-thread model (ARCH-5) and single-threaded epoll network loop (ARCH-22) are realized across `daemon/netloop.c` (accept + per-connection TLS + frame dispatch), `shared/framebuf.c` (incremental frame reassembly implementing the ARCH-9 two-phase read over a bounded buffer), `daemon/dbwriter.c` (the DB-writer thread that owns the write connection and runs migrations on boot), and `shared/tls.c` (ARCH-10/51). Connections use non-blocking I/O with epoll interest re-armed from mbedTLS `WANT_READ`/`WANT_WRITE`. The **net thread ↔ DB-writer thread hand-off** is a job/result queue: the net thread submits AUTH/SEND jobs and is woken to collect results by the writer's **eventfd** registered in epoll, so all socket I/O stays on the net thread and all DB writes on the writer. The loop implements handshake → `WELCOME`/`REJECT` (PROTOCOL.md §3), AUTH → `AUTH_OK`, `SEND` → persist (monotonic id ARCH-43, idempotency ARCH-44) → `SEND_ACK` to the sender + `BROADCAST` to the channel's connected members (REQ-090/092), and reconnect backfill (REQ-100/101): a `BACKFILL_REQUEST` becomes a read job that replays `id > cursor` messages (membership-checked, bounded) as `BROADCAST`s followed by `BACKFILL_DONE` (ARCH-46). **AUTH is currently stubbed** (the token is upserted as a user subject, with a default channel auto-joined) — the real two-mode auth + session design (ARCH-19/55–60, [AUTH.md](./AUTH.md)) replaces it as a follow-on milestone. `daemon/main.c` wires these together with the `/healthz` responder (ARCH-25).
- **ARCH-53 (Logging):** The daemon logs to **stderr**, not syslog. Under systemd (a self-hosted `.deb`, ARCH-20) journald captures stderr automatically (`journalctl -u openchimed`); in a container (the hosted model on Fly.io, or any containerized self-host; ARCH-4/36) the runtime collects stdout/stderr — whereas a container typically has no syslog daemon, so `syslog()` would go nowhere. This is the standard "log to stderr, let the supervisor route it" model; a self-hoster wanting syslog can set journald's `ForwardToSyslog`. A leveled-logging helper (info/warn/error with timestamps) is a later refinement of the destination, not a change to it.
- **ARCH-28 (Packaging and process model):** One binary, multiple processes. The daemon self-forks (or re-execs itself with a mode flag, e.g. `openchimed --mode=audio-sidecar`) to run companion processes like the audio relay (ARCH-18) as separate OS processes. Process isolation comes from `fork()`, not from being a separate build artifact, so this gets the same crash-isolation property as a separate binary while keeping one build artifact and a guaranteed version match between the daemon and its sidecars.
- **ARCH-29 (Upgrade rollout):** Restart-and-reconnect. A new daemon binary replaces the old one and restarts the process; connected clients see a dropped connection and reconnect automatically via the mechanism REQ-100/REQ-101 already require. No graceful connection draining — not worth the added complexity at single-box-per-tenant scale (ARCH-4).

## Wire Protocol

- **ARCH-6 (Decision):** Custom length-prefixed, versioned binary protocol over TLS/TCP. Not HTTP, not WebSocket, not JSON. Justified because both ends (C daemon and C client) are built together, removing any reason to pay HTTP/JSON overhead.
- **ARCH-7 (Serialization):** Explicit field-by-field; no struct memcpy.
- **ARCH-8 (Frame layout):** Fixed header of `length` (u32, network byte order), `version` (u8/u16), `msg_type` (u16), followed by a type-specific payload.
  - `length`: total bytes after this field; makes the stream self-framing over TCP's boundary-less byte stream.
  - `version`: checked on the first frame so incompatible clients are rejected cleanly rather than misparsed.
  - `msg_type`: enum discriminating login, message-send, message-broadcast, presence-update, ack, error, etc.
- **ARCH-9 (Reading discipline):** Network thread reads in two phases (fixed header, then `length` more bytes), each looping to handle partial TCP reads. Everything is network byte order, converted at the edges.
- **ARCH-10 (TLS):** The daemon generates its own self-signed certificate on first run. Clients trust it via TOFU (trust-on-first-connect) pinning, with the fingerprint optionally published in the `.well-known` discovery metadata (ARCH-14) for out-of-band verification. This governs how a **client trusts a daemon**. The reverse relationship — the daemon acting as a client of someone else's public service, i.e. an S3-compatible object store (ARCH-70) — deliberately uses ordinary **CA-chain verification** instead: there is no fingerprint to pin, providers rotate certificates freely, and accepting any certificate would expose credentials and attachment bytes. That is the one place OpenChime consults a CA bundle. This applies uniformly across all three deployment models (ARCH-76) — no ACME, no Let's Encrypt, no certificate renewal machinery anywhere in the baseline system. Standard PKI was the original design but was dropped: the client is a native binary under the maintainer's control, not a browser, so it doesn't need CA-chain trust; and mandatory ACME is impossible for a self-hosted, internet-unreachable deployment (e.g. an air-gapped MSP client network), since ACME requires public HTTP reachability or a public DNS API. This is a different axis from the earlier per-operator cert-pinning design that was dropped in favor of a generic client — that was build-time pinning tied to per-operator binaries; TOFU is dynamic, runtime pinning, fully compatible with one generic client. The one exception is the incoming-webhooks endpoint (see "HTTP and Webhooks" below), which does need a CA-signed cert.
- **ARCH-30 (Protocol limits):** Conservative small-team defaults: max frame size and max message body size are ~64KB, and max concurrent connections per tenant is in the low hundreds. Attachments are never sent as protocol frames — they go through the object-storage path (ARCH-17) exclusively. The byte-exact limits (`MAX_FRAME_SIZE` = 65 KiB, `MAX_BODY_SIZE` = 64 KiB) are fixed in [PROTOCOL.md](./PROTOCOL.md) §2.1.
- **ARCH-41 (Handshake and version negotiation):** A connection opens with a client `HELLO` advertising the inclusive `[min_version, max_version]` range it supports; the server replies `WELCOME` with a single chosen version used by both sides thereafter, or `REJECT` with a reason code. The `HELLO`/`WELCOME`/`REJECT` frames are frozen at version 1 forever so negotiation itself can never hit a version mismatch. `REJECT` distinguishes `VERSION_TOO_OLD` (client outdated — prompt "update the app") from `VERSION_TOO_NEW` (daemon behind — operator must upgrade, do not prompt the user), resolving REQ-111. First-frame-must-be-`HELLO` and pre-parse version validation resolve REQ-110. Detailed layout in [PROTOCOL.md](./PROTOCOL.md) §3.
- **ARCH-42 (Primitive field encodings):** All frames are composed from a fixed primitive set — `u8/u16/u32/u64` big-endian, `str` (u16-length UTF-8), `lstr` (u32-length UTF-8 for message bodies), `bytes` (u32-length raw), and `idem` (fixed 16-byte token) — encoded explicitly field-by-field with no struct `memcpy`, realizing ARCH-7. Timestamps are `u64` ms since Unix epoch UTC; ids are `u64`. Catalogued in [PROTOCOL.md](./PROTOCOL.md) §7.
- **ARCH-43 (Message id allocation):** Message ids are server-assigned `u64`, monotonic per tenant, allocated by the single DB-writer thread (ARCH-5) inside the WAL commit. Tenant-monotonicity means ascending id order equals accept order within a channel, which is what makes REQ-092's per-channel ordering guarantee and the client dedup high-water mark (ARCH-45) fall out for free.
- **ARCH-44 (Idempotency mapping):** A `SEND` carries a client-generated 16-byte idempotency token; the daemon persists a `(channel_id, idempotency_token) → message_id` mapping in SQLite and, on a repeat token, re-returns the original `SEND_ACK` instead of storing a second copy. This makes an unacked send safely retryable (REQ-093) and de-duplicates offline-composed messages re-sent on reconnect (REQ-102). The mapping is pruned after a bounded retention window (24h, **implemented** in `daemon/dbwriter.c`: the writer runs a time-gated `DELETE FROM sent_messages WHERE created_at_ms < now - retention` at most once per interval), long enough to cover realistic reconnect-retry.
- **ARCH-45 (Client-side dedup):** A client keeps a per-channel high-water mark of the highest `message_id` seen and suppresses any `BROADCAST` with `message_id <=` that mark as a redelivery, satisfying REQ-091's at-least-once duplicate suppression. The dedup key is the server message id (ARCH-43); the window is the client's persisted per-channel mark.
- **ARCH-46 (Reconnect backfill shape):** On reconnect the client sends `BACKFILL_REQUEST` carrying a per-channel `{channel_id, after_message_id}` cursor list; the server replays `BROADCAST` frames for `message_id >` each cursor in ascending order per channel, terminated by `BACKFILL_DONE`. Per-channel (not a single global) cursors are required because cross-channel ordering carries no guarantee (REQ-092), so a single global cursor could skip a low id still missing in one channel while a higher id was already acked in another. Resolves REQ-101. Detailed in [PROTOCOL.md](./PROTOCOL.md) §6.
- **ARCH-47 (Error frame and code table):** Post-handshake errors use a single `ERROR` frame carrying a `u16` reason code, a `fatal` flag (whether the connection closes), an optional `context` blob (the offending idempotency token on a failed `SEND`), and a human-readable message; handshake-stage version errors use `REJECT` with the same code space. Codes are grouped by range (1000 protocol/version, 2000 auth, 3000 messaging, 9000 internal) so a client can categorize an unrecognized code. Full table in [PROTOCOL.md](./PROTOCOL.md) §8.

## Client

- **ARCH-11 (Language):** Native C, explicitly rejecting Electron. Reinforced by ARCH-74 (the shared client core is C).
- **ARCH-74 (Client model — one C app-core, native UI per platform):** **Supersedes the single-custom-rendered-client approach** (and demotes ARCH-12/62/63/65, below). The client is split into a **shared, frontend-agnostic C app-core** (`client/core/`) — the network thread, session, local store, the **view-model** (channels, messages, roster, presence, unread), and the **reducers** that fold server events into it and turn user intents into frames — and **thin native frontends** that only render the model and emit intents. Each platform gets its **native UI**: a **TUI** over a terminal cell grid; **Win32** on Windows, **GTK** on Linux, **AppKit** on macOS/iOS, **Android** views on Android; and a **DOM UI** for web (the desktop toolkits and their language realities are settled in ARCH-80, which refines this line) (WASM can't use native desktop widgets). This is the *tdlib* model (a shared C/C++ core under fully native UIs) — chosen for real native feel (OS-provided text input, IME, accessibility, high-DPI, notifications) over the consistent-but-non-native look of a custom-rendered single UI. The trade is more total UI code (one per platform), bounded by keeping **all** logic and state in the core so a frontend is pure view+input. The core is **headless-testable** — a test drives it against the in-process daemon and asserts the view-model — so it is CI-covered with no UI. Build order: the app-core + the **TUI** first (fastest usable, testable client; no rendering-stack complexity), then the native GUIs. Full design in [CLIENT.md](./CLIENT.md).
- **ARCH-75 (TUI toolkit — termbox2 + utf8proc, both MIT, text-only):** The first frontend over the app-core (ARCH-74) is a terminal UI built on two tiny, permissively-licensed single-file libraries: **termbox2** (MIT) for the terminal **cell grid + input**, and **utf8proc** (MIT) for **Unicode display width + grapheme-cluster segmentation**. The reason a toolkit matters here at all is one property specific to a chat client: **correct wide-character / emoji width** — OpenChime has emoji reactions (REQ-070/071) and wrapped message panes, and a single mis-measured emoji or CJK glyph corrupts a whole terminal layout. utf8proc supplies exactly that (`utf8proc_charwidth` + UAX #29 grapheme breaking, with the Unicode Character Database tables bundled and maintained upstream), so we get the hard part right without hand-rolling or yearly UCD updates; termbox2 supplies the grid + key/mouse input over plain POSIX termios with **zero transitive dependencies**, so we own the layout/plane logic ourselves (which we were writing anyway). **notcurses was evaluated and rejected on licensing:** it is the more batteries-included option but hard-depends on **libunistring (LGPL, copyleft)**, whereas termbox2 + utf8proc are both **MIT with zero copyleft**, keeping the entire linked client permissive — the deciding factor given the project's license posture (mbedTLS Apache-2.0, SQLite public-domain, jsmn MIT). Both libs are **vendored as committed single-file source** in `third_party/` (like jsmn — `termbox2/termbox2.h`, `utf8proc/utf8proc.{c,h}` + the generated `utf8proc_data.c`), pinned to a release (termbox2 v2.5.0, utf8proc v2.11.3), and compiled straight into the `tui` target — no build system, no `apt`/`brew` dependency, identical across local/CI. **The TUI never renders graphics — no images, ever** (a deliberate scope decision): it is a pure text/emoji cell grid (channel sidebar with presence, a wrapped scrolling message pane, an input line). **Interaction is modeless** (weechat/irssi/Slack): the input line is always ready to type (Enter sends), **actions are `/`-commands**, navigation is Ctrl/Alt chords — **the `/`-command interaction here is superseded by ARCH-83** (menu/screen-driven + a Ctrl+K command palette; the slash dispatcher was deleted). A modal/vim scheme is rejected because it taxes every message with an `i` first. The TUI builds on the host like the daemon (`make tui`), no cross-compile, no container. Native GUIs (Win32/AppKit/Android/DOM, ARCH-74) are separate frontends over the same core and do not use termbox2. Full design in [CLIENT.md](./CLIENT.md).
- **ARCH-80 (Desktop GUI strategy — pure-C native per platform, no cross-platform toolkit, no .NET):** Refines ARCH-74's "native UI per platform" into a concrete toolkit-and-language decision for the three desktops, after evaluating and rejecting the alternatives on the record.

  **Rejected:** .NET/C# (a runtime dependency the project will not take), WinUI 3 via C++/WinRT (drags in a C++ toolchain and the Windows App SDK runtime for the modern look — not worth it when the message list is custom-drawn anyway), Qt (C++, draws its own non-native widgets, LGPL), and the C-over-C++-toolkit path (wxWidgets via the moribund `wxc`, or an owned C++ shim — either way accepts C++ in the tree). The two purpose-built C toolkits that wrap native controls, **IUP** (MIT) and **libui-ng**, were the closest fit and were rejected for one reason: **their macOS story is X11 or an out-of-mainline Cocoa fork**, which is worse than writing the AppKit shell directly, so they buy nothing on the one platform where a cross-platform toolkit would have earned its keep.

  **Decision — hand-written native frontend per desktop, over the shared C core (ARCH-74), using each platform's own native API:**

  | Platform | Native GUI API | Language | Notes |
  |---|---|---|---|
  | **Windows** | Win32 + **Direct2D/DirectWrite** (custom surfaces) + native controls (**RichEdit**/menus/dialogs) | **pure C** | the Win32 API *is* a C API; maximally native, zero runtime dependency. Rendering stack settled in **ARCH-82** (comctl32 was the first draft; replaced) |
  | **Linux** | GTK | **pure C** | GTK is a C library (GObject) and *is* the native Linux toolkit |
  | **macOS** | AppKit | **Objective-C** | there is no pure-C native GUI on modern macOS — Carbon was removed in Catalina (2019), and AppKit is Objective-C classes. Obj-C is a strict *superset* of C, so the `.m` UI layer calls `oc_client` directly with no FFI and no marshalling; only the macOS UI shell is non-C, which Apple leaves no way to avoid |

  The message transcript is **custom-drawn in every option** — no desktop toolkit ships a virtualized, variable-height chat-transcript control (Win32 `LVS_OWNERDATA` + DirectWrite, GTK `GtkDrawingArea`, AppKit `NSView`). What the native toolkit buys is everything *around* the transcript: window chrome, text input with IME, dialogs, dark mode, high-DPI, accessibility, notifications — exactly ARCH-74's rationale. So a cross-platform toolkit would not have saved the hard part regardless.

  **Distribution reality (researched, and it differs by platform):** static linking — the daemon's virtue (vendored mbedTLS + SQLite) — **does not extend uniformly to the GUI.** Windows links to one self-contained `.exe` cleanly, because Win32/comctl32 live in the OS. **Linux cannot cleanly static-link**, and this is a property of the GTK ecosystem, not a toolkit choice: `gdk-pixbuf` loads image decoders as dynamic modules from a runtime cache, so a static binary silently fails to render icons. The native Linux answer is therefore a package or an **AppImage/Flatpak** that bundles the `.so`s, like every GTK app. macOS ships a `.app` bundle of frameworks regardless. This expectation is set now rather than discovered mid-build: the single-static-binary philosophy fits the daemon and the Windows client, not a native Linux GUI.

- **ARCH-81 (Client port order — Windows TUI before Windows GUI):** The core (`client/core/`) is written against POSIX; a Windows client needs three seams closed first — **pthreads** (`queue.c`, `net.c`), **`res_query`** DNS SRV (`resolve.c`, → `DnsQuery`), and **sockets** (already shimmed in `shared/sock.h`). Rather than close those seams *while simultaneously* building a Win32 GUI in an unfamiliar API — where every bug is ambiguous between the port and the UI — the port is validated first against a **Windows TUI**, a frontend already trusted on Linux. It exercises the entire ported core (threads, DNS, sockets, store, TLS) end to end, so any later Win32-GUI bug is unambiguously a GUI bug.

  **Terminal-backend note (verified).** A Windows TUI is well-trodden — the Windows Console API (`SetConsoleMode` / `ReadConsoleInput` / `WriteConsoleOutput`, pure Win32 C) is the foundation, and since Windows 10 the console interprets ANSI/VT sequences once `ENABLE_VIRTUAL_TERMINAL_PROCESSING` is set (default under Windows Terminal / ConPTY), so the *output* half of a POSIX TUI largely works and only input/resize/mouse need Console-API handling. What is missing is a *drop-in for termbox2 specifically*: **termbox2 is POSIX-only** (`/dev/tty`, termios) and, unlike the original termbox, dropped the WinAPI-console backend (ARCH-75 pins termbox2 for the POSIX build). The bounded path — chosen because termbox2 is a thin grid+input surface and `client/tui/main.c` owns all layout on top of it — is to write a small **termbox2-API backend over the Windows Console API**, leaving the TUI source unchanged. PDCurses (public-domain, maintained, Win95→Win11) is the alternative foundation but is a different API, so it would need an adapter too. Either way this is a bounded, known piece of work, not a research risk — but it is real code, not a free recompile.

  **Status (DONE):** the Windows TUI shipped and ran on real Windows (the Console-API termbox2 backend, `client/tui/termbox2_win.c`), validating the core port (threads/DNS/RNG/sockets/store/TLS) end to end. So ARCH-81's precondition is satisfied and the Windows *GUI* work (ARCH-82) proceeds against a trusted core.

- **ARCH-82 (Windows GUI rendering — Win32 + Direct2D/DirectWrite + RichEdit; a self-rendered unified GUI was tried and rejected):** Settles the Windows rendering stack, refining ARCH-80's Windows row (comctl32 → Direct2D/DirectWrite + RichEdit) and recording two rejected first drafts so the reasoning isn't relitigated.

  **What was tried and rejected (2026-07):** (1) A **comctl32** GUI (login + chat) — proved the core end-to-end but stock Common Controls look unavoidably dated (a config-dialog aesthetic), and modernizing them is its own owner-draw slog. (2) A **self-rendered, cross-platform-*consistent* GUI** — **Clay** (single-header layout) on **raylib** (OpenGL window + GPU + stb_truetype text). Login + chat were built and *looked* modern, but it was rejected on principle: a self-rendered UI owns every pixel and therefore **re-implements everything the OS gives a native app for free** — text input, IME, selection, clipboard, context menus, native scroll physics, accessibility, OS theming, high-DPI, the title bar. That is a permanent lag behind native and hundreds of hours of approximation (the canonical example: on WSLg the GLFW character callback is dead, forcing a hand-rolled US-QWERTY key→char translator just to type). It also contradicts ARCH-74's whole rationale (native feel), and since the product is **native-per-platform, not one consistent look**, the unified approach had *no* rationale left. Clay + raylib are removed; `client/gui` is deleted.

  **Decision (LOCKED):** the Windows shell renders with **Win32 + Direct2D + DirectWrite (+ WIC)** for the custom surfaces (message transcript, channel sidebar, rails — none of which any toolkit ships), and **native controls for the hard bits**: **RichEdit** (composer — text editing, IME, selection, clipboard, undo, and bold/italic/lists for free), **EDIT** (search), **Win32 menus** (`TrackPopupMenu`, context + dropdown), **comdlg32**/dialogs (file picker, create-channel, prefs). Direct2D is **GDI's modern GPU successor** (built on D3D11/DXGI) — *not* GDI; DirectWrite renders **native color emoji** (`ENABLE_COLOR_FONT`), turning raylib's hardest deferral into a built-in. Pure C throughout; Direct2D-from-C is COM-vtable boilerplate, wrapped once in a few helpers. The `oc_client` shell wiring from the comctl32 draft (WinMain, window, native-control hosting) carries forward; only the ugly *view* is discarded, along with the shared-core fixes it motivated, which **stay** (e.g. `oc_resolve` calling `oc_sock_startup` so `getaddrinfo` works before `WSAStartup` on Windows; the `oc_thread`/`oc_port` shims).

  **Interaction model (applies to all native GUIs):** **affordance-driven — buttons, menus, dialogs, drag-and-drop — never slash commands.** The `/`-command UX belongs to the TUI (ARCH-75, modeless terminal input); porting it into the GUI was a category error. A normal application's user never types a command to create a channel, attach a file, or react to a message — they click a `+`, a paperclip, a reaction button, or a right-click menu. This is a hard requirement of every GUI frontend, distinct from the TUI.

- **ARCH-83 (TUI toolbox — an in-tree `tuikit` widget library, not a framework port):** The TUI **was redesigned** from its mIRC-style slash-command UX (ARCH-75) to a menu/screen-driven, discoverable interface (menus + a Ctrl+K/':' command palette; the slash dispatcher was deleted). That redesign needs reusable widgets, which today exist only as ad-hoc, chat-specific helpers buried in `client/tui/main.c` (~2284 lines), with keybinding hints as hardcoded strings that drift from the actual key handling. The decision: build **`tuikit`**, a self-contained in-tree C library that **merges the terminal layer (termbox2 + the Windows console backend from ARCH-81 + utf8proc width) with a small widget set, a formatting/style layer, and a keymap/help model** — the shared TUI toolbox. Full design in [TUIKIT.md](./TUIKIT.md).

- **ARCH-84 (Federated enrollment client — the daemon's first outbound federated call):** For a federated/hosted workspace, the daemon must obtain the opaque `audience` id that central mints OIDC tokens for (§3.3/§3.6). The daemon side of that enrollment is `daemon/enroll.c`: gated on `OC_ENROLL_URL`, on first boot it **generates its own ECDSA-P256 keypair + a random ≥128-bit audience** (`ws_…`), **persists** them (migration 0017 — a single-row `enrollment` table, the same key-survival pattern as the TLS identity, ARCH-66b), and prints an **`oce1.` enrollment code** to stderr for the operator to courier into the control-plane console (the same "print a one-time code" idiom as the first-run setup token). It then **calls out** — the daemon's first outbound federated request, over the S3 client's CA-verified HTTPS transport (ARCH-70), never the reverse (ARCH-56) — to fetch a challenge nonce, sign a proof-of-possession (ASN.1-DER ECDSA over `openchime-enroll-v1|<aud>|<nonce>`), and confirm; central activates the binding. The **enrolled audience then feeds the OIDC verifier** (§3.4), so relay tokens minted for it validate. The enrollment *mechanism* + registry are the control plane's (a separate private repo); this is only the daemon's client half. Config, not runtime-config-fetch, so ARCH-26 holds.

  **What it is:** `tk_term` (merged terminal), `tk_draw`/`tk_style` (width-correct text + Lip Gloss-style boxes), five widgets (`tk_list`, `tk_input`, `tk_textarea`, `tk_viewport`, `tk_modal`), `tk_key` (bindings-as-data → generated footer/help, killing the hint-drift), and optional `tk_spinner`/`tk_progress`/`tk_filepicker`. Widgets are plain C structs with an init/handle-event/draw triad the app drives from its own loop.

  **What it is NOT:** a Bubble Tea / Charm runtime port. We evaluated porting the whole Go stack (Bubble Tea's Model/Update/View runtime + async Cmd loop + all of Bubbles) and **rejected it** as scope/maintenance we don't need — we already have an event loop, and `client/core` is already Model+reducer. Charm (MIT) is the *design reference* we reimplement a subset of, not a dependency. `tuikit` takes the widget/keybinding/formatting designs; it skips the runtime.

  **Hard boundary — generic + reusable:** `tuikit` depends only on `third_party/termbox2` + `utf8proc` and **never** includes `client/core`/`oc_model`/anything OpenChime-specific. Widgets render generic data through a delegate callback; the chat app supplies delegates that read `oc_model`. So the chat TUI becomes an *app built on the toolbox*, and `tuikit` is independently reusable (and archivable as `libtuikit.a`). Chat-specific code (the `build_*_rows` family, panel `layout`, `ws_session`, `config.c`, `secret_backend.c`) stays in `client/tui/`. Build order (all shipped): merge the terminal layer + primitives with zero behaviour change, then `tk_key`, then the widgets (with a standalone `tuikit/demo.c`), then migrate the chat TUI onto them behaviour-preserved, then (separately) **the menu/screen UX redesign this all existed to enable** — 256-color theme, tk_palette command launcher, arrow-nav, Ctrl+X key hints.

- **ARCH-13 (Generic client):** A single generic client replaced the earlier per-operator custom-binary approach.
- **ARCH-61 (Repo layout):** Client and daemon live in one repo, split into `shared/` (the wire contract: `protocol`, `tls`, `framebuf`), `daemon/` (server), and `client/` (app). The client links the *exact* `shared/` source the daemon uses, so the two cannot drift on the protocol — the same rationale that made `tests/e2e_client.c` reuse `shared/protocol.c`. A separate client repo was rejected: it would need a submodule or a vendored copy of the wire code, reintroducing drift risk. Full design in [CLIENT.md](./CLIENT.md).
- **ARCH-62 (Client loop and threading — partly superseded by ARCH-74):** The two-thread model (UI/render thread + blocking-socket network thread, communicating over mutex+condvar queues) is kept and now lives in the app-core + each frontend; the raylib `AppCtx`/`app_frame` specifics are dropped. Original: The client uses openblocks' loop shape — one `AppCtx` struct + one `app_frame()` driven by a swappable loop driver (desktop `while`, later emscripten/iOS callbacks) — with a **two-thread** model layered on: a UI thread that only renders/inputs, and a **network thread** that owns the TLS socket (connect → handshake → auth → read/dispatch). The two communicate through mutex+condvar queues (the daemon's net↔dbwriter pattern); the UI thread drains the inbound queue at the top of `app_frame()`. The network thread uses **blocking** sockets (its own thread, one connection — no epoll needed), lifting `tests/e2e_client.c`'s connect/read/write logic.

App state (`client/app.c`) is kept raylib-free and separate from rendering. raylib's built-in font is used first; the HarfBuzz + Unicode line-break message view (ARCH-12) lands behind the seam in a later phase.

Stored under the platform config dir with tight file perms; platform keychains are noted future hardening. (Phase 1 is in-memory; the store lands with the reconnect/offline phase.)
- **ARCH-65 (Client build — superseded by ARCH-74):** The raylib/mingw cross-compile is dropped; each native frontend builds with its platform toolchain over the shared core (the TUI builds on the host like the daemon). Original: The client is built the openblocks way — a flat Makefile target per platform that vendors raylib + mbedTLS for that target (via `scripts/build_raylib_*.sh` / `build_mbedtls_windows.sh` into per-platform `third_party/*` prefixes) and compiles `client/*.c` + `shared/*` directly. **No build container:** a Debian container was tried and dropped — it only works for the Linux desktop target, whereas the other targets (macOS/iOS can't be containerized; Windows/Android use their own toolchains), so it doesn't generalize and diverges from the daemon's host build. This iteration targets **Windows only** (`make windows`: mingw-w64 cross-compile on Linux/CI to a static `.exe`, no Windows machine needed); Linux/macOS/wasm/Android/iOS follow. Cross-platform requires a small **socket-portability shim** (`shared/sock.h`, POSIX vs Winsock) used by `shared/tls.c`'s BIO callbacks and `client/net.c`, behind `#ifdef _WIN32` — the Linux daemon is unaffected. Release artifacts are produced by CI/CD (a future release workflow), never a dev machine.
- **ARCH-66 (Read-only query connection):** A refinement of the two-thread model (ARCH-5). Read-only query jobs — reconnect backfill (ARCH-46), full-text search (ARCH-15), and the `LIST_*` enumerations (channels, users, thread replies, reactions) — run on a **third thread with its own `query_only` SQLite connection to the same WAL database**, off the single writer thread. SQLite WAL allows one writer and many concurrent readers without blocking, so a heavy search or large backfill no longer stalls message sends or auth for the tenant (supports REQ-211's concurrency goal). Implemented in `daemon/dbwriter.c`: `oc_dbwriter_submit` routes jobs by type into a write queue (writer thread, the sole mutator) or a read queue (reader thread); both push onto the one result queue the net thread drains via the eventfd. All mutating jobs — including AUTH, which mints sessions and provisions users — stay on the writer, preserving the single-write-path invariant.
- **ARCH-67 (Presence — in-memory, net-thread):** Online/away/offline (REQ-120) is derived entirely from live connection state on the **network thread**, never persisted — presence is ephemeral and rebuilds itself from the current connection set on restart, so a durable table would only add write load and staleness. A user's aggregate status is a fold over their connections: **online** if any connection is active, **away** if all are away, **offline** once the last closes. State transitions fan out a tenant-wide `PRESENCE_UPDATE` to every *other* authenticated connection (a client tracks its own presence locally), and a newly authenticated client receives a one-shot snapshot of every currently-online user. Sends are best-effort (`presence_send` appends and flushes but never closes a connection, avoiding a `conn_close`↔broadcast recursion); a dropped presence frame is self-correcting on the next transition. Implemented in `daemon/netloop.c` with a `presence` field per connection and `ep`/`conns` threaded through the read path.
- **ARCH-68 (Typing — reader-thread membership relay):** The transient "user is typing" indicator (REQ-121) is relayed, not stored: a `TYPING` signal becomes an `OC_JOB_TYPING` **read job** on the query connection (ARCH-66), which resolves the channel's members so the fan-out is **scoped to members** — private-channel and DM typing never leaks to non-members. The net thread then delivers `TYPING_UPDATE` to each connected member except the sender. There is no server-side expiry timer or "stopped typing" frame; the **client** expires the indicator locally after ~6 seconds (resolving REQ-121's open expiry-window question), refreshed by each new `TYPING`. Running membership resolution on the reader thread keeps a burst of typing signals off the single write path.
- **ARCH-69 (Attachment transfer — proxied and chunked over the pinned wire):** File bytes flow **through the daemon** over the client's existing pinned-TLS connection, chunked into ordinary frames (PROTOCOL.md §5.14) — never via presigned URLs to a directly-reachable object store. This resolves REQ-141's access-control `[needs ARCH decision]`: because every byte traverses the daemon, authorization is a single in-daemon check on the **same membership path as reading the message** (`channel_read_access`), with no signed-URL scheme, no TTL, and no object-store ACL to configure or trust. The proxied choice is forced by two existing invariants: **TOFU cert pinning** (ARCH-10) gives the client exactly one trusted cert — the daemon's — and no CA bundle, so it cannot validate a second (object-store) endpoint; and the **island model** (ARCH-4/26) keeps the object store private, with the daemon the only publicly reachable component of the tenant's own box. Presigned URLs would violate both (a second public endpoint with a CA-signed cert, exactly the complication REQ-171 flagged) and would mean *more* client code (a second HTTP+TLS stack), whereas proxied reuses the one wire the client already speaks. The cost lands on the **daemon, not the client**: transfers must never block the single epoll net thread (ARCH-5) or blow the per-connection 1 MiB output cap. So blob I/O runs on a **dedicated transfer worker pool** (`daemon/xferpool.c` — a small pool, default 2, off both the net loop and the DB threads, in the spirit of ARCH-66), and chunks move between it and the net thread via a submit/result queue plus **eventfd** registered in epoll, exactly the shape of the net<->DB-writer hand-off (ARCH-52). **The ordering rule is that at most one job per transfer is in flight**: the next chunk is submitted only when the previous completes. That makes chunk order automatic, lets N workers run safely without pinning a transfer to one of them (concurrent jobs always belong to different transfers), and supplies backpressure for free. Backpressure is therefore explicit at both ends: uploads use the server-advertised in-flight **window** (`UPLOAD_ACK`, now sent when a chunk is durably written rather than merely received) plus net-thread **read-pausing** — while a job is in flight the connection drops `EPOLLIN` *and* stops draining buffered frames, so TCP throttles a fast sender and the frame buffer cannot overflow; downloads simply don't request the next slice while the out-buffer is above the soft cap, resuming on `EPOLLOUT` drain. **Ownership across a closing connection** is the subtle part: a job carries a `conn_id` (never a `conn *`, and ids are never reused) and the blob handle travels *with the job*, so a completion arriving for a connection that has already been freed still owns a valid handle and releases it instead of leaking. A teardown that finds a job in flight must not release the handle itself — it leaves the connection paused and lets the completion clean up. Chunk payloads stay under `MAX_FRAME_SIZE`, so the framebuf/parse path is unchanged. An attachment is linked to a message as message metadata — a **self-describing optional trailing attachment list** on `SEND` (ids in) and `BROADCAST` (metadata out): written only when non-empty and read only when trailing bytes remain, so a message with no attachments is byte-identical to the pre-attachment layout and no protocol-version bump is needed (client and daemon share the codec). Backfill re-attaches a message's linked attachments so a reconnecting client also sees them; DMs and thread replies (the same optional list on `SEND_REPLY`/`THREAD_REPLY`, surfaced live and via `LIST_THREAD`) ride the identical path.
- **ARCH-73 (Audio call model — per-channel, ephemeral roster, relay-only server):** An audio call (REQ-150) is **one per channel** (`call_id == channel_id`), and its roster is **ephemeral in-memory state on the net thread** (like presence, ARCH-67) — no DB rows, reset on restart, since a call is transient live state. `CALL_JOIN` is authorized by the ordinary channel-read gate (a read job on the query connection, ARCH-66, like typing); the net thread then owns all roster mutation and delivery — `CALL_JOINED` to the joiner (with their private media endpoint), `CALL_ROSTER` to the others on every change. Crucially, the **server never decodes Opus**: the daemon and its sidecar treat audio as opaque bytes and *relay* (ARCH-18), so there is no libopus dependency server-side — the codec lives entirely in the client. **REQ-152 (loss/rejoin) resolved:** a participant is dropped on `CALL_LEAVE` or TCP disconnect (the `conn_close` path removes them and re-rosters the rest), but the call persists while ≥1 participant remains; rejoin is a fresh `CALL_JOIN` minting a new token, and the media side mirrors this with a UDP silence timeout in the sidecar. The media path is **built**: the daemon forks the relay at startup (`daemon/audio_sidecar.c`, ARCH-28 — a fork, not a re-exec; it binds the UDP socket, pairs a Unix socket for IPC, and the child exits on IPC EOF when the daemon dies), the net thread mints a 16-byte per-join bearer token, registers it with the sidecar over the Unix socket (`AUTHORIZE`/`REVOKE`, ARCH-31), and advertises the sidecar's UDP port + token in `CALL_JOINED`. The sidecar learns each participant's UDP address from their first packet and forwards opaque payloads to the other participants of the same call, tagged with the sender's id; it never decodes Opus (no server-side codec dependency). A `REVOKE` on `CALL_LEAVE`/disconnect and a UDP silence sweep (`OC_AUDIO_SILENCE_MS`) mirror REQ-152 on the media side. The client's Opus encode/decode + UDP I/O is Phase-2 client work.
- **ARCH-72 (Notification preferences — server-authoritative, device-synced):** A user's notification settings (REQ-130/131) live on the server, not per-device: a per-channel **level** (all / mentions / none) in `notification_prefs` and a **do-not-disturb** daily window (minutes-of-day, UTC) as columns on `users` (SCHEMA.md migration 0012). `SET_NOTIFY_PREF` / `SET_DND` mutate them on the DB-writer thread and `LIST_NOTIFY_PREFS` reads them; every one of these returns a full `NOTIFY_PREFS` snapshot which the net thread pushes to **all of the user's connections**, so a change on one device syncs to the others (the same fan-out-to-a-user pattern as presence). These are the settings clients honor and the deferred push gateway (REQ-132/133) will consult; consistent with REQ-131, DND governs push only — in-app unread/badges derive from messages and are unaffected. The push *transport* (APNs/FCM, ARCH-16) and the per-message notify *decision* (mention matching + DND gating) are the remaining mobile-push milestone; this lands the durable, synced configuration they build on.
- **ARCH-71 (Incoming-webhook token, payload, and scope):** Resolves REQ-170's open decisions. A webhook is a **per-channel bearer token**: 32 random bytes shown once at creation (hex in the URL), stored only as its **SHA-256** in the `webhooks` table (SCHEMA.md migration 0010), exactly like a session token (ARCH-58) — a leaked DB never yields a usable token, and lookup is one indexed probe on `token_hash`. It is minted by a channel member via the `CREATE_WEBHOOK` binary frame (returning `WEBHOOK_INFO`), so creating a webhook requires the same post access as sending. The receiver is **`POST /webhook/<token>`** over the ALPN-demuxed HTTP handler (ARCH-32/54): the daemon hex-decodes the token, hashes it, resolves the channel + creator on the **DB-writer thread** (`OC_JOB_WEBHOOK_POST`), and posts the body as an ordinary message **authored by the webhook's creator** — so it fans out through the same `BROADCAST` + backfill path as any message, with no special delivery. The **payload** is deliberately minimal and forgiving: `application/json {"text": "..."}` (parsed with the vendored jsmn) or a raw `text/plain` body, capped at `MAX_BODY_SIZE`; an empty message is a 400, an unknown/disabled token a 404. A **per-token fixed-window rate limit** (60/min, the shared `ratelimit` module) keeps one noisy integration from flooding a channel. A webhook post carries a **display-name override** (the webhook's label): persisted as a nullable `messages.author_name` (migration 0011) and delivered as an optional trailing `author_name` field on `BROADCAST` — so the post shows as e.g. "GitHub CI" rather than the human who created the webhook, consistently live and via backfill. Webhooks are also **manageable**: `LIST_WEBHOOKS` returns a channel's webhooks (ids/labels/disabled, never tokens) and `DELETE_WEBHOOK` removes one (any channel member), after which the token stops resolving. The one piece **not** built is REQ-171's on-demand CA-signed certificate (ARCH-34) — the endpoint is currently served on the daemon's existing cert, which is sufficient for controlled senders and tests but not for uncontrolled third parties that validate against a CA store; on-demand issuance is the remaining infra work.
- **ARCH-70 (Blob storage adapter seam):** Attachment blobs live in **object storage, never in SQLite** (implements ARCH-17; the SQLite `attachments` table holds only pointers + metadata, SCHEMA.md migration 0009), reachable behind a narrow **backend vtable** (`daemon/blob_backend.h`: open/close, streaming put begin/chunk/commit/abort, streaming get begin/chunk/close, delete) so the backend is swappable. **Two backends ship**, selected by configuration (see below): the default **local filesystem** (`blobstore.c` — stage-to-`.tmp`-then-atomic-rename, ideal for a single-box island) and **S3-compatible** (`blob_s3.c`) — a minimal **SigV4** signer (`daemon/sigv4.c`), path-style, streaming the body with `x-amz-content-sha256: UNSIGNED-PAYLOAD` so nothing is buffered whole; chosen over a heavy AWS SDK. The S3 transport is **HTTPS with CA-chain and hostname verification** (`oc_tls_client_init_ca`), since every public provider is HTTPS-only and SigV4 credentials plus attachment bytes must not cross an unauthenticated channel; plaintext remains reachable via an explicit `http://` scheme or a non-443 port for a local S3 implementation on a private network. Verified end-to-end against **Tigris** (a real provider): streaming multi-chunk round-trips byte-for-byte, correct size reporting, delete semantics — and, negatively, that expired, self-signed, untrusted-root, and wrong-hostname certificates are all rejected. The daemon streams to/from the adapter in bounded chunks, matching the output-cap discipline that governs message fan-out. A blob is written under an opaque storage key on `UPLOAD_END` and its `attachments` row is committed on the DB-writer thread (the single write path). Blob I/O runs on the ARCH-69 transfer worker pool, not inline on the net thread, so a slow S3 endpoint no longer stalls the event loop. Storage reclamation and pressure handling are ARCH-77. **Selection is by configuration, not a mode flag:** when S3 credentials are present the S3 backend is used, otherwise the local-filesystem backend is; OpenChime ships no object-storage *server* of its own and never has — where S3 is used, the daemon is purely a **client** of an operator-supplied S3-compatible provider.

## Discovery

- **ARCH-14 (Rule):** Workspace-address, resolved by plain DNS — **there is no resolution *service*, in any deployment model** (ARCH-76). At sign-in the client collects the **workspace** (the tenant's address) plus the user's **email** directly, the same model as Slack's "enter your workspace URL." The workspace is turned into a daemon address by ordinary DNS, with no shared, always-on, cross-tenant lookup component to run: consistent with the island model (ARCH-4) and the "no runtime configuration dependency" stance (ARCH-26). Note the DNS *records* under the service suffix (forms 2 and 3 below) are maintainer-provided and so are counted as a federated function in ARCH-76 — but they are static records, not a request-serving component, so no lookup traffic reaches the project. Three forms, one per deployment model:
  - **Own domain (stand-alone, or federated declining the DNS function):** the user supplies a full domain (e.g. `chat.acme.com`), resolved via SRV records plus optional `.well-known` metadata (which may also carry the TOFU cert fingerprint per ARCH-10). Nothing the project operates is involved.
  - **Hosted:** the user supplies a bare name (e.g. `acme`); the client appends the service's known DNS suffix as a pure client-side string convention (`acme` → `acme.openchime.example`) and resolves the result by plain DNS. The per-tenant DNS record is provisioned when the tenant is created — DNS *is* the name→address map, so no custom registry service exists. The user may equivalently type the full `acme.openchime.example`.
  - **Vanity name (self-hosted federated, optional, free):** a federated self-hoster may request a DNS record under the service suffix (e.g. a CNAME `acme.openchime.example` → their own box) so their users get the same short-name experience as hosted tenants without the self-hoster owning or configuring public DNS. This stays a pure DNS record, not a runtime service, so it does not reintroduce the resolution layer, and no lookup traffic reaches the project. It composes cleanly with TOFU TLS (ARCH-10): because the client pins whatever self-signed cert the daemon presents rather than validating a CA chain against the hostname, a name under someone else's domain "just works" with no cert coordination — a synergy that a CA-cert design would not have. The box remains fully self-hosted (operator's config, object storage, and **all message data**, per ARCH-4/ARCH-26); only the discovery name lives under the service suffix.
  - **Port:** resolution yields a port as well as a host, with precedence SRV-record port > `.well-known` `port` field > the default 443 (ARCH-54). A self-hoster on a non-standard port is honored automatically via SRV; hosted tenants use 443.
  - The email is used only to drive the OIDC login (ARCH-19); it is not used to derive the workspace (a hosted tenant's email domain does not reveal its address without a lookup registry, which this design deliberately avoids — the workspace/audience registry ARCH-56 keeps for OIDC is not consulted for discovery). This supersedes the earlier "dot-based, resolve bare names via a hosted resolution service" rule, which required the shared cross-tenant component that ARCH-4's island model otherwise avoids; see REQ-041.

- **ARCH-77 (Storage pressure — reclaim, evict, refuse):** The daemon assumes an **unmanaged box** (REQ-212–216): nobody is watching the disk, so it has to stay alive on finite storage by itself. Local-backend only — with external S3 the blobs are off-box and only the database grows locally.

  Three tiers fire in strict order, cheapest and least destructive first, driven by two watermarks (a *pressure* threshold that starts reclamation and a lower *recovery* target it works down to, so the daemon doesn't oscillate at a single boundary):

  1. **Reclaim (REQ-213)** — a periodic sweep frees what nothing was promised to keep: staged `.tmp` bytes from aborted or interrupted uploads, and blobs orphaned by message deletion or never referenced by any message. Time-gated so an in-flight upload is never swept, mirroring the `sent_messages` pruning pattern (ARCH-44). Note `oc_blob_delete` exists but had no caller before this decision — orphaned blobs accumulated indefinitely, so this tier alone recovers real space on any long-lived box.
  2. **Evict (REQ-215)** — if reclamation didn't reach the recovery target, attachment blobs are deleted **oldest-first, automatically, by default**. The `attachments` row is *kept* and marked unavailable — a tombstone, so the client renders "no longer available" instead of failing an opaque download, and the message history stays complete (REQ-053 is untouched; only bytes go, never messages). A configured **grace period** exempts recent uploads so a file shared into a live conversation cannot vanish mid-discussion. Each eviction is audited (REQ-251) and surfaced (REQ-214). An operator may disable this tier, which promotes tier 3 to the terminal state.
  3. **Refuse (REQ-216)** — if space is still below the floor, `UPLOAD_BEGIN` is rejected with a distinct error. Refusal happens **at declaration, not mid-transfer**: the client declares the size up front, so the daemon can decline before a byte moves rather than failing a half-finished upload.

  **The database reserve is inviolable (REQ-212).** A configured floor of free space belongs to SQLite and is never available to attachment bytes, so exhausting attachment storage degrades the box to "attachments unavailable" and never to "chat down" — the one outcome an unattended box must not reach, since a full disk stops writes, blocks WAL checkpointing, and takes messaging down with it.

  **Deliberate durability trade.** Tier 2 destroys user-visible data without a human deciding, which is a real cost — sharpened by ARCH-3, since this repo ships no replication and an unmanaged self-hosted box may have no backup at all. It is default-on regardless because the alternative on the target deployment is a dead tenant; the grace period, tombstones, audit trail, oldest-first ordering, and the disable switch exist to bound that trade rather than to hide it.

- **ARCH-78 (Storage maintenance pass):** The housekeeping of ARCH-77 runs as a single **periodic maintenance pass** (REQ-218) rather than as work scattered across request handlers.

  **It runs on a timer, not opportunistically.** The daemon already has a time-gated prune — `maybe_prune_idem` (ARCH-44) drops old `sent_messages` rows — but that one piggybacks on the writer loop and so only fires when writes are happening. That is fine for idempotency rows and wrong here: **an idle tenant is exactly the one whose disk fills with nothing prompting a cleanup**. The pass is therefore driven by the net loop's existing 500 ms `epoll_wait` tick, gated to its own interval, so it fires on a quiet box too. The interval and the maximum attachment age are configuration (REQ-217), and both are overridable so a test can compress the clock the way `oc_dbwriter_set_idem_retention` already allows.

  **Work is split across the three threads by what each owns.** Finding what to remove is a query, so the *writer* selects expired or orphaned rows (age past the configured maximum, aborted uploads, blobs whose message is gone). Deleting the bytes is I/O that can block on an S3 round trip, so it goes to the **transfer pool** (ARCH-69) as fire-and-forget jobs, never inline on the net loop. The metadata row is tombstoned by the writer once the blob delete is queued. This is the same seam the upload path already uses, so no new threading model is introduced.

  **Each pass is bounded.** It deletes at most a fixed number of blobs per run and re-checks free space between batches, so a box that is badly over its limit recovers across several passes instead of stalling the daemon in one long sweep — housekeeping must never compete with message delivery (REQ-212).

  Free space comes from `statvfs` on the blob directory, sampled once per pass and cached — so the upload admission check (REQ-216) costs no syscall on the hot path. An **unmeasurable filesystem reads as unconstrained**: guessing "pressured" would make the daemon destroy user data because a syscall failed, which is a far worse outcome than doing nothing. Built in `daemon/storage.c` (policy + measurement), `process_storage_maint` (the writer-side tiers), and `maybe_run_maintenance` (the tick).

- **ARCH-79 (Audit log):** REQ-251's log is an `audit_log` **table in the tenant's own database** (migration 0016), not a separate file and not a hash chain.

  *Why a table in the same database.* "Kept outside the normal message store" is satisfied by being its own table with its own access path — it shares no schema, no query surface, and no read permission with messages. A second SQLite file was considered and rejected for this scope: it doubles the connection and backup story (ARCH-3 already makes backup the operator's own affair) for a threat model this design does not otherwise defend against. **Append-only is a write policy, not a guarantee** — the daemon emits only INSERT, and never UPDATE or DELETE except the age-based prune below. An operator with the database file can still rewrite history; detecting that would require a hash chain, which is the natural upgrade if REQ-252's compliance work ever demands tamper-*evidence* rather than tamper-*discouragement*. That tradeoff is recorded here rather than hidden.

  *Bounded, and partitioned.* The log ages out with everything else on the ARCH-78 maintenance pass. The subtlety is REQ-251b: the catalog deliberately includes **failed authentication and denied privileged actions**, whose volume an unauthenticated attacker controls. A single global cap would therefore hand that attacker a way to evict the record of their own earlier successful actions — the audit trail becomes an evidence-shredder. So the cap is **per family** (administrative / account / security / moderation): each ages against its own budget, and a flood of security noise cannot touch administrative history. This is why the `family` column exists and is indexed.

  *Never the secret.* Entries record that a password changed, never the password; that an invite was redeemed, never the token; that authentication failed for a username, never the attempted password. An audit log is a high-value target precisely because admins read it, so it must not become a place where credentials accumulate.

  *Read path.* `AUDIT_QUERY` / `AUDIT_PAGE` (PROTOCOL.md), owner/admin only, authorized in the **writer against the user's current role** — the same shape as ARCH-77's storage report, so a demotion takes effect mid-session. The TUI renders it as an Audit log overlay (the Ctrl+K launcher's "Audit log"), newest first, paged. Reads are ordinary queries on the read connection (ARCH-66); writes go through the writer like every other mutation, so the log inherits the same single-writer ordering as the data it describes.

## Feature Implementation

- **ARCH-15 (Search):** FTS5 full-text search, positioned as a competitive wedge against Slack's history caps.
- **ARCH-16 (Notifications delivery):** Push via APNs/FCM. Consequently **push is available in the self-hosted federated and hosted models and is absent in self-hosted stand-alone**, where mobile clients fall back to in-app/foreground notification. The gateway learns *that* a notification is due and for whom, never message content (the ARCH-76 invariant). Concrete design is deferred: REQ-132/133.
- **ARCH-17 (Attachments):** Via object storage.
- **ARCH-18 (Audio conferencing):** Server-relay (no P2P/ICE), Opus codec, delivered as an isolated UDP-based sidecar process rather than embedded in the daemon's TCP loop. The full design — the huddle model, client-side mixing (forced by the server never decoding), the duplex audio engine, and acoustic echo cancellation — is [AUDIO.md](./AUDIO.md).
- **ARCH-31 (Audio sidecar IPC):** The daemon and the audio sidecar process (ARCH-18, ARCH-28) communicate over a Unix domain socket — native POSIX IPC via the same `socket()` API already used for TCP, no extra library, no network exposure.

## HTTP and Webhooks

- **ARCH-32 (Embedded HTTP listener):** The daemon embeds an HTTP/1.1 listener, fed from the same event loop as the binary-protocol listener (ARCH-22). It shares TLS port 443 with the binary protocol, demultiplexed by ALPN rather than sitting on a separate port (see ARCH-54 — this supersedes the earlier "separate port on 80/443" phrasing). Parsing is a **small purpose-built HTTP/1.1 request reader** (`daemon/http.c`) for this one POST endpoint — not a general embedded web server; picohttpparser (MIT/Perl) was the planned vendored parser and remains the option if the HTTP surface ever grows beyond the webhook receiver. Mongoose was ruled out (GPLv2/commercial dual license, not MIT/BSD); civetweb was ruled out because it brings its own connection-handling loop that would compete with ARCH-22's event loop. This endpoint serves the incoming-webhook receiver (REQUIREMENTS.md REQ-170, ARCH-71); the health check stays on its own plaintext port (ARCH-25).
- **ARCH-33 (No HTTP/2):** The webhook/health HTTP surface is plain HTTP/1.1 only, matching ARCH-6's existing rejection of HTTP overhead for the core protocol. Webhook senders are third parties making single, independent requests; HTTP/2's multiplexing has no benefit for that pattern.
- **ARCH-34 (Webhook TLS):** A CA-signed certificate is obtained on-demand, feature-gated to tenants that enable webhooks — not a baseline daemon requirement (ARCH-10). This is the one surface where TOFU pinning doesn't work: third-party webhook senders (GitHub, Zapier, scripts) are not under the operator's control and validate TLS against a standard CA trust store with no ability to pin a custom cert. Because the HTTP surface shares port 443 with the binary protocol via ALPN (ARCH-54), the daemon presents this CA cert to connections that do not negotiate the `oc/1` ALPN (typically selected by SNI matching the webhook hostname) and the self-signed cert (ARCH-10) to `oc/1` connections.
- **ARCH-54 (Ports and ALPN multiplexing):** The public port is **443** for all external traffic — the binary protocol and the HTTP/webhook surface (ARCH-32) share it, demultiplexed by **ALPN** negotiated in the TLS handshake: a client offers `oc/1` (`OC_ALPN_PROTO`) and is routed to the binary-protocol handler; anything else (e.g. an HTTPS webhook sender) is routed to the HTTP/1.1 handler. 443 was chosen because it is the one port restrictive networks reliably allow outbound and the only port third-party webhook senders speak; a high port would work for the app clients in most environments (outbound high ports are usually open) but not for the webhook case, and standardizing avoids a per-environment variable. The daemon binds a configurable `OPENCHIME_PROTO_PORT` (production 443 — self-hosted via a systemd `CAP_NET_BIND_SERVICE` grant per ARCH-20, hosted via Fly's external→container port map; dev binds unprivileged 8443). **Clients** dial the port from discovery with precedence SRV-record port > `.well-known` `port` > `OC_DEFAULT_PORT` (443). The `oc/1` ALPN and the 443 default are a fixed client-facing contract established now (in `shared/tls.c`, both server and client) so clients conform from first release even though the HTTP handler is a later milestone; the `/1` suffix versions the transport-framing generation, separate from the per-frame `version` (ARCH-8). Full detail in [PROTOCOL.md](./PROTOCOL.md) §1.1.

## Authentication

Full design and rationale in [AUTH.md](./AUTH.md).

- **ARCH-19 (Architecture):** Two authentication modes selected per deployment (ARCH-55), converging on a daemon-issued session (ARCH-58). In **local mode** the daemon is the identity authority (username+password, ARCH-59). In **OIDC mode** the login is a client-drives-browser flow with PKCE using platform-native auth session APIs (ASWebAuthenticationSession on iOS/macOS, loopback redirect on desktop), but the OIDC Relying Party is the maintainer's **central service** (ARCH-56), not the daemon: the daemon validates an **ES256 JWT that the central service re-issues** (ARCH-57), against a single pinned key — never a raw *provider* JWT and never provider JWKS. This supersedes the original "the daemon validates the returned provider JWT against provider JWKS" rule — that pulled JWKS fetching + multi-provider handling into the lean C daemon and gave self-hosters no path to social login without registering their own provider apps.
- **ARCH-55 (Two-mode auth framework):** Authentication is **local** (daemon-managed accounts) or **OIDC-via-central** (social login brokered by the project's central service). The two map onto the deployment models (ARCH-76): **self-hosted stand-alone is necessarily local**, since OIDC is a federated function; **self-hosted federated** may use either, and choosing OIDC *is* how it opts in to that function; **hosted** uses OIDC. Local mode therefore stays fully air-gappable. There is deliberately no "daemon speaks OIDC directly to your own IdP" mode — OIDC always routes through central — which keeps the daemon free of JWKS fetching and multi-provider handling (it verifies one JWT from one pinned key, parsing the claims with a small vendored JSON reader, ARCH-57) and means self-hosters never hold provider credentials. A deployment picks one mode in config (ARCH-26); the daemon advertises it in-protocol via `AUTH_CHALLENGE` (PROTOCOL.md §4). Both modes converge on a daemon-issued session (ARCH-58), so all messaging/reconnect/revocation is mode-agnostic. v1 is one mode per tenant; both-at-once is deferred.
- **ARCH-56 (Central OIDC service + relay):** The maintainer runs a central service that holds the real Google/Microsoft/Apple app credentials, runs the Authorization-Code-+-PKCE flow, and re-issues an OpenChime ES256 JWT (ARCH-57) audience-scoped to the target workspace. The **client is the courier** — it carries the token from central to the daemon, so central never connects to a self-hosted daemon (preserving the island model, ARCH-4). Trust is a public key the daemon pins from config (bundled in the distribution); the dependency on central is **login-time only** (issued sessions survive a central outage; local mode has no central dependency). This is one of the federated services of ARCH-76, contacted at **login time only** and brokering **identity only** — consistent with REQ-041, which forbids any shared component in the message/data path. Central also keeps the **workspace/audience registry** (which `audience` ids are valid). The `audience` id is an **opaque random identifier** bound to the workspace when it enrolls; central mints a token only for a registered audience. It is deliberately **not** the workspace's DNS name (superseding the earlier `aud = acme.example` illustration in AUTH.md), so OIDC identity stays decoupled from discovery (ARCH-14) and survives a workspace changing or adding a name. That registry is part of the federated OIDC function and is never consulted for discovery (ARCH-14). (The enrollment mechanism itself is a control-plane concern, outside this repo.) The central service is a separately-built web component; the daemon side is tested with a test issuer.
- **ARCH-57 (Identity token — ES256 JWT):** Central signs a standard **JWT** with **ES256** (ECDSA P-256 + SHA-256) using its key; the daemon validates it by **pinning both the key and the algorithm** — it requires `alg = ES256` and rejects anything else, which closes JWT's classic footguns (`alg=none`, RS256/HS256 confusion) — then verifies the signature with mbedTLS (ES256 maps directly to mbedTLS ECDSA-P256; Ed25519/EdDSA is not supported by mbedTLS), and checks the `iss`, `aud` (== this workspace's configured opaque id — not its hostname; no cross-workspace replay), and `exp` claims. Claims are parsed with a vendored single-file JSON tokenizer (jsmn, MIT, zero-allocation — one small dependency in the same spirit as picohttpparser). A bespoke compact token was considered (to avoid the JSON parser) and rejected: JWT is a standard, battle-tested format with well-understood mitigations, which is what security-critical validation wants, and the JSON cost is negligible for a once-per-login token (ARCH-6's "no JSON overhead" rule targets the high-frequency message path, not the auth bootstrap).
- **ARCH-58 (Daemon-issued session tokens):** After any successful auth, the daemon mints a random 32-byte session token returned to the client and stores only its SHA-256 (leak-resistant) with user id + expiry + last-seen in a `sessions` table (SCHEMA.md migration 0002). Reconnect re-presents the token (no re-auth, REQ-100); the session lifetime is the daemon's, not a provider token's (REQ-181); revocation is a row delete (REQ-182 — the local session table the flag asked for). This convergence makes everything downstream mode-agnostic.
- **ARCH-59 (Local-auth credential model):** Local accounts use username+password hashed with PBKDF2-HMAC-SHA256 (mbedTLS `mbedtls_pkcs5_pbkdf2_hmac`, per-user salt, ~600k iterations) — chosen to add no new dependency (mbedTLS has no argon2; argon2 is a future vendored upgrade). The first owner is bootstrapped from a one-time setup token (config/log, no email → air-gapped-safe); further users are created by invite token. Failed attempts are rate-limited per account and per source (resolves REQ-191). Passwords travel only inside TLS (REQ-180) and only the hash is stored.
- **ARCH-60 (Role storage and enforcement):** Every user holds one tenant role — `owner`/`admin`/`member` — stored as a `role` column on `users` (migration 0002). Enforcement lives in the DB-writer handlers (the single write path): the ≥1-owner invariant (REQ-030), admin/owner moderation delete via `messages.deleted_by` (REQ-032), and owner/admin-only tenant invite/remove (REQ-033). Resolves the role storage/enforcement `[needs ARCH decision]`.

## Local Development and Build

- **ARCH-35 (Build system):** A single hand-written `Makefile` (no CMake, no autotools), mirroring the sibling OpenBounty project's convention.
- **ARCH-36 (Local dev/test harness):** Docker Compose, not QEMU or Firecracker. Fly.io actually runs machines on Firecracker microVMs — Docker only shares the host kernel via namespaces/cgroups, so this doesn't replicate that isolation boundary — but it's the format Fly.io itself ingests as a build artifact (a Dockerfile becomes a Firecracker rootfs via `flyctl deploy`), and was chosen for local iteration speed and simplicity over fidelity.
- **ARCH-37 (Local base image):** Alpine (musl libc), matching the lean 256MB-per-tenant memory target (ARCH-4/REQUIREMENTS.md REQ-210). 
- **ARCH-38 (Local S3 simulation):** MinIO stands in for a managed S3-compatible store in the local Docker Compose environment, over LocalStack (heavier, broader-than-needed AWS emulation) and SeaweedFS (less battle-tested). MinIO server is AGPLv3-licensed; this is a dev/test-only dependency run via Compose, never embedded or distributed with OpenChime's own code, so no obligation attaches. It currently has no consumer — the daemon's S3 blob backend (ARCH-70) defaults to the local filesystem and is not wired into compose.
- **ARCH-39 (Container startup sequencing):** The container's entrypoint initializes a fresh WAL-mode database if none exists, then execs the daemon in the foreground. (This decision previously also sequenced a replication sidecar; that moved out with ARCH-3.)
- **ARCH-40 (Dev convenience scripts):** A `Scripts/` directory wraps the Docker Compose workflow: `run.sh` (build + start + block until the health check passes), `stop.sh` (stop, preserving local volumes), `reset.sh` (stop and wipe local volumes, for a from-scratch start). These are thin wrappers with no behavior of their own beyond what `docker compose` already does directly — they exist to remove manual steps (creating `.env`, polling `/healthz`, remembering the container-removal-before-volume-removal ordering), not to hide anything.
- **ARCH-48 (Test strategy and CI):** Two tiers, detailed in [TESTING.md](./TESTING.md). Unit tests are hand-rolled (a ~15-line `CHECK` macro, no vendored framework), live in `tests/`, `#include` the `.c` under test directly to reach file-static helpers, and run via `make test` compiled `-O0 -g` — the same convention as the sibling C project openblocks. They cover pure logic: the frame codec (the first target), migration runner, idempotency/dedup, rate limiter, and the protocol state machine, using an injectable clock/id source for determinism. Integration tests drive the daemon with an in-repo C test client that **links the same `shared/protocol.c` the daemon uses** — not a second-language reimplementation that could silently drift from the wire format — run against the existing Docker Compose stack (ARCH-36/38/39) so the deployed image is exercised as a black box. CI is GitHub Actions triggered on PRs to `main` (doc-only changes skipped), mirroring openblocks' `paths-ignore`/`concurrency` conventions: a `build` job (compile + `make test`) and an `integration` job that brings up the compose stack and drives the protocol vertical against it. The client-side TLS library needed for socket-level integration scenarios is not yet decided and is flagged in TESTING.md §3.1 as part of the daemon TLS work.
